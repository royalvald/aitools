# Auto BugFixer 边界定义（第一阶段）

> 本文档是项目的最高优先级设计文档：先确定边界，再细化流程。
> `01-需求分析.md` 与 `02-整体方案.md` 中的流程细节以本文档界定的范围为准，
> 边界未确认的项（见第 10 节）确认后再回头细化流程设计。
>
> 每条边界项标注状态：✅ 已确定 / 🟡 建议默认（待确认）/ ❓ 待确认（阻塞设计）。

## 1. 系统定位边界

**Auto BugFixer 是：**
- 一个串行处理 bug 的自动化流水线工具，连接"bug 单 → 代码修复 → 测试环境部署 → 接口级验证"四个环节。
- 一个人机协同系统：机器做分析和执行，人做确认、审批和兜底。

**Auto BugFixer 不是：**
- ❌ 不是 bug 管理系统（不替代 Jira/禅道，只读取和回写）。
- ❌ 不是 CI/CD 平台（不接管构建发布体系，只复用现有部署方式）。
- ❌ 不是无人值守的全自动系统（关键环节有人工闸门）。
- ❌ 不是测试平台（不管理用例，只执行针对单个 bug 的验证计划）。

状态：🟡 建议默认

## 2. 业务边界（处理链路的两端）

```
【边界外】测试提 bug 单 → 【边界内】读取 → 分析 → 修复 → 部署 → 验证 → 报告 → 【边界外】人工复核/上线
```

| 环节 | 边界内 | 边界外 |
|------|--------|--------|
| bug 提交与定级 | — | ✅ 测试同事按现有流程提单 |
| bug 读取与分析 | ✅ | — |
| 代码修复 | ✅（Claude Code） | 修复失败时转人工 |
| 修复 diff 审批 | ✅（本地文档审阅） | — |
| 测试环境部署 | ✅ | 生产部署 |
| bug 级验证 | ✅（接口断言） | 全量回归测试 |
| 验证报告与复核发起 | ✅ | 最终复核结论（人做） |
| 代码合并、上线 | — | ✅ 研发按现有流程执行 |

状态：🟡 建议默认

## 3. 人机职责边界

| 事项 | 机器 | 人 |
|------|------|-----|
| bug 分类、可验证性评分 | ✅ 执行 | 低分时兜底判断 |
| 验证计划生成 | ✅ 生成草案 | 中分档审阅确认/修改（本地文档） |
| 代码修复 | ✅ 执行 | 修复 diff 审批（可配置）；失败时接管 |
| 部署执行 | ✅ | 部署失败时接管 |
| 验证执行与报告 | ✅ | 复核验证报告，做最终结论 |
| 合并代码、上生产 | ❌ 不做 | ✅ |
| 修改流水线配置、阈值 | ❌ | ✅ |

原则：机器永远可以"提议"，涉及代码去向（合入、上线）的决定永远在人。

状态：🟡 建议默认

## 4. 功能边界清单（第一阶段）

### 4.1 In Scope（做）

- [ ] 导入 Bugzilla 导出的 bug 记录文件（支持多种导出格式，解析器可插拔）；Bugzilla REST API 接入待确认后作为可选增强
- [ ] LLM 分析：分类、可验证性评分、验证计划草案生成
- [ ] 评分路由：≥80 全自动 / 40-79 人工确认 / <40 仅修复+部署
- [ ] 本地文档审阅机制（验证计划确认、修复 diff 审批）
- [ ] Claude Code headless 调用执行修复（串行、单工作区、失败重试上限）
- [ ] SSH 部署到测试环境（复用现有部署脚本/命令）+ 健康检查 + 失败回滚
- [ ] 接口验证执行器（HTTP 请求、JSONPath 断言、步骤间变量传递、清理步骤）
- [ ] 验证失败反馈重修（总轮次上限）
- [ ] 验证报告生成（本地文档）；bug 单评论/状态回写依赖 Bugzilla API 确认，未确认前以本地报告为准
- [ ] 模板库与修复记忆库（memory）读写与注入
- [ ] 全链路日志与存档（分析结果、diff、部署日志、验证报告、审阅文档）

### 4.2 Out of Scope（第一阶段明确不做）

- ❌ 多 bug 并发处理、多工作区
- ❌ 自动合并代码、自动上生产
- ❌ Web UI / 专门的人机交互页面（审阅一律本地 Markdown 文档）
- ❌ UI 自动化验证（Playwright 页面操作类验证）
- ❌ 全量回归测试
- ❌ 向量检索（memory 第一阶段只做模块+关键词匹配）
- ❌ 运行指标看板
- ❌ 多项目/多仓库同时接入（第一阶段只接 1 个被修项目）
- ❌ bug 系统的双向深度集成（第一阶段以导出文件导入为主，API 直连与评论回写视 Bugzilla 版本确认后增强）

状态：🟡 建议默认，逐条可议

## 5. 系统集成边界

| 外部系统 | 交互方向 | 方式 | 降级策略 | 状态 |
|----------|----------|------|----------|------|
| bug 管理系统（Bugzilla） | 读（文件导入为主） | 解析 Bugzilla 导出文件（多格式，可插拔解析器）；REST API 待确认版本后可选接入 | 无 API 时回写降级为本地报告文档 | 🟡 已定为 Bugzilla，API 可用性待确认 |
| Claude Code | 调用 | headless CLI 子进程 | 失败重试 N 次后转人工 | ✅ |
| 分析用 LLM | 调用 | API | 与修复共用 Claude，不可用时仅阻断分析环节 | ✅ 代码外发合规已确认允许 |
| 被修项目仓库（Go） | 读写 | 本地 git 工作区 | 工作区不干净则暂停告警 | ✅ |
| 测试环境 | 部署+验证 | SSH + 自研部署流程（无现成脚本，从零实现）+ HTTP 健康检查 | 部署失败回滚并转人工 | ✅ |
| 通知渠道 | — | 第一阶段不做提醒，纯本地审阅 | — | ✅ |

## 6. 数据边界

**进入系统的数据**：bug 单内容、被修项目代码（在运行机器本地）、测试环境接口响应。

**系统产生的数据**：分析结果、验证计划、修复 diff、审阅文档、验证报告、memory 记录 —— 全部存于运行机器 `data/` 目录，不上传第三方。

**红线**：
- 密钥（bug 系统 token、SSH 私钥、LLM API Key）只走环境变量/本地配置，不进 git 仓库、不写入报告文档。
- 生产环境数据、生产凭据一律不进入系统。
- 喂给 LLM 的内容限于 bug 单 + 代码片段；代码外发至 Claude API 的合规性已确认允许。✅

## 7. 环境边界

- 流水线运行在**一台固定机器**上（研发本地或一台测试服务器），单实例串行运行。
- 部署目标**仅限测试环境**；预发/生产不在第一阶段范围内。
- 被修项目代码在运行机器上有本地仓库，修复直接在工作区进行。
- 测试环境需具备：SSH 可达；健康检查手段由部署模块自行实现（HTTP 或进程检查）。

## 8. 技术边界（第一阶段）

- Python 单进程应用，SQLite 持久化状态，不上消息队列/工作流引擎。
- 人机交互载体：本地 Markdown 审阅文档 + `resume` 命令，不做服务端。
- 配置即代码：YAML 配置 + 环境变量，不做配置管理后台。
- 串行单工作区：同一时刻只处理一个 bug。

状态：✅ 已确定（前期讨论结论）

## 9. 质量与代价边界

- 单 bug LLM 成本上限：可配置，超限转人工。🟡
- 单 bug 修复-验证最大轮次：默认 3，超限转人工。🟡
- 修复 diff 审批：默认开启（可配置关闭）。🟡
- 不追求修复成功率指标承诺，第一阶段目标是跑通链路并积累 memory。

## 10. 决策点确认记录

已确认（2026-07-26）：

1. ✅ **bug 系统**：Bugzilla。考虑到 API 可用性不确定，第一阶段以**导入 Bugzilla 导出文件**为主要 bug 来源，需支持其多种导出格式（CSV/XML 等），解析器可插拔。
2. ✅ **被修项目技术栈**：Go。
3. ✅ **部署现状**：无现成部署脚本，部署模块需从零实现（构建 → 传包 → 重载 → 健康检查全流程）。
4. ✅ **通知渠道**：第一阶段不做提醒，纯本地审阅文档。
5. ✅ **合规性**：允许将 bug 单内容和代码片段发送至 Claude API，修复模块按 Claude Code headless 方案推进。

仍待确认：

6. ❓ **Bugzilla 版本及 REST API 可用性**——Bugzilla 5.0+ 自带 REST API，若环境支持则 bug 读取和评论回写都可从"文件导入/本地报告"升级为 API 直连，请确认部署版本。
7. ❓ **测试步骤真实样例 2-3 个（脱敏）**——决定分析 prompt 和验证计划结构能否落地。

## 11. 边界变更规则

- 任何"要不要做 X"的讨论，先对照第 4 节清单；不在清单内的默认为 Out of Scope。
- 边界变更需修改本文档并注明日期与理由，流程文档随之联动更新。
