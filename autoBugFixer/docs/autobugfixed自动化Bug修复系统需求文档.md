## 二、项目背景与目标

### 2.1 项目背景

在日常软件研发与迭代过程中，缺陷（Bug）的修复占据研发与测试人员大量精力：从缺陷信息收集、原因定位、代码修改，到重新打包部署、回归验证，整个链路长且高度依赖人工操作，重复性高、响应周期长。随着 AI 编码助手（如 Claude Code）能力的成熟，将缺陷修复流程自动化已具备可行性。

autobugfixed 旨在构建一套端到端的自动化 Bug 修复系统：自动读取缺陷管理平台中的 Bug 列表，完成信息补全与优先级评估，调用 AI 编码能力完成代码修复，随后在测试环境中自动完成软件换包、重启与功能验证，并将修复经验沉淀至本地知识库，实现修复能力的持续自我优化。

### 2.2 项目目标

1. **效率目标**——将标准 Bug 从上报到验证关闭的平均处理周期缩短 60% 以上，减少研发在重复性修复工作上的投入。
2. **自动化目标**——对信息完整、难度适中的 Bug 实现"获取—修复—验证—关闭"全流程无人值守处理。
3. **质量目标**——修复后回归验证通过率不低于人工修复基线，不产生新的引入性缺陷。
4. **沉淀目标**——建立可持续演进的修复经验知识库，使系统修复成功率随使用次数逐步提升。

### 2.3 成功度量指标

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 自动修复成功率 | 无需人工介入即完成修复并通过验证的 Bug 占比 | 首期 ≥ 40%，一年内 ≥ 60% |
| 平均修复周期 | Bug 从进入系统到验证关闭的平均耗时 | 较人工基线缩短 60% |
| 回归通过率 | 修复后按预处理方案验证通过的比例 | ≥ 95% |
| 知识库复用率 | 命中历史经验的修复任务占比 | 半年内 ≥ 30% |

## 三、名词定义

| 术语 | 定义 |
|------|------|
| Bug / 缺陷 | 缺陷管理平台中记录的软件问题单，包含标题、描述、复现步骤、环境信息、附件等字段 |
| 预处理 | 修复前的准备阶段，包括数据获取与转换、完整性分析、验证方案生成、难度评分排序 |
| Claude Code | AI 编码助手，系统通过其完成代码理解、修改与修复结果输出 |
| 回归验证 | 修复完成后，按预处理阶段生成的验证方案对 Bug 功能点进行复测确认 |
| 本地记忆 | 系统本地持久化的修复经验库，记录修复过程分类、经验条目与不适用场景 |
| 知识库沉淀 | 将验证有效的修复经验结构化输出，供后续任务检索复用 |
| 人工介入点 | 流程中需要人工确认或补充信息的节点，如信息补全、方案确认、失败讨论 |

## 四、用户角色与使用场景

### 4.1 用户角色

| 角色 | 职责描述 | 与系统的交互 |
|------|----------|--------------|
| 测试工程师 | 在缺陷平台提交、跟踪 Bug | 提交 Bug；补充系统判定缺失的缺陷信息；查看修复与验证结果 |
| 研发工程师 | 负责疑难问题修复与方案评审 | 处理系统转人工的 Bug；评审自我优化迭代的经验变更 |
| 运维工程师 | 维护测试环境与部署链路 | 配置测试环境连接与命令行工具；处理部署异常告警 |
| 项目/质量负责人 | 关注修复效率与质量 | 查看修复看板、成功率与优先级排序结果 |

### 4.2 典型使用场景

1. **场景一：全自动修复**——系统在缺陷平台发现一条信息完整、难度评分较低的界面显示类 Bug，自动完成代码修复、测试环境换包验证并关闭缺陷单，全程无需人工参与。
2. **场景二：信息补充介入**——系统分析发现某 Bug 缺少复现步骤与报错日志，自动向提交人发起信息补充请求，待信息补全后继续自动流程。
3. **场景三：方案确认介入**——系统生成回归验证方案后，因涉及核心交易链路，推送至研发负责人确认执行规划，确认后自动执行修复与验证。
4. **场景四：修复失败转人工**——系统对某 Bug 多次修复仍未通过验证，将其标记为无法自动修复，明确不适用场景并生成待人工讨论的议题，转交研发处理。

## 五、系统总体业务流程

系统以流水线方式处理每一个 Bug，总体流程分为五个阶段：

1. **阶段一：预处理**——从缺陷管理平台获取 Bug 数据并转换为标准结构；分析信息完整性，必要时请求人工补充；生成后续回归验证方案并视情况请求人工确认；基于解决难度、回归验证难度与改动项给出综合难度评分并排序，确定修复优先级。
2. **阶段二：Bug 修复**——自动感知 Bug 在页面、数据库、接口请求三个层面的具体表现；对接 Claude Code 执行代码修复并获取修复结果。
3. **阶段三：回归与验证**——连接测试环境，调用命令行工具完成软件重新打包、更新与启停；按预处理阶段生成的验证方案执行 Bug 功能验证。
4. **阶段四：本地记忆**——对本次修复过程进行分类，与已有修复经验比对，将新经验写入本地经验库；对无法修复的部分，明确不适用场景并生成需人工进一步讨论的议题。
5. **阶段五：自我优化**——在人工介入评审的前提下，基于沉淀的经验对系统策略进行优化迭代，并将知识库成果对外输出。

> 流程说明：预处理评分未达标或方案未获确认的 Bug 不进入自动修复阶段；修复结果未通过回归验证时，系统将按重试策略再次修复，达到重试上限后转入本地记忆阶段处理并升级人工介入。

## 六、功能需求

功能需求按模块划分，每条需求包含编号、描述、输入、输出与优先级。优先级定义：**P0** 为首期必须实现，**P1** 为首期后尽快实现，**P2** 为规划实现。

### 6.1 预处理模块

预处理模块负责将原始 Bug 数据加工为可执行修复任务，并通过评估与排序形成修复队列。

#### 6.1.1 FR-PRE-01 数据获取与转换（P0）

系统应能对接缺陷管理平台，自动读取 Bug 列表及单条 Bug 的完整信息（标题、描述、复现步骤、期望结果、实际结果、环境版本、日志与截图附件、关联代码仓库与分支等），并转换为系统内部统一的标准数据结构。

| 项目 | 内容 |
|------|------|
| 输入 | 缺陷平台 Bug 列表与详情（API 或页面采集） |
| 输出 | 标准化 Bug 任务对象（含全部原始字段与转换后的结构化字段） |
| 规则 | 支持定时轮询与事件触发两种获取方式；字段缺失时保留空值并标记，供完整性分析使用 |

#### 6.1.2 FR-PRE-02 Bug 完整性分析及优化（P0）

系统应分析每条 Bug 信息的完整性与可修复性，判断复现步骤、环境信息、错误现象等关键要素是否齐备；对信息不足的 Bug，自动生成信息补充请求并推送人工介入，待补充完成后重新进入分析流程。

| 项目 | 内容 |
|------|------|
| 输入 | 标准化 Bug 任务对象 |
| 输出 | 完整性评估结论（完整 / 待补充）；待补充项清单与补充请求 |
| 规则 | 可能涉及信息补充，需要人工介入；补充请求应明确列出缺失字段与建议内容 |

#### 6.1.3 FR-PRE-03 回归验证方案生成（P0）

系统应基于 Bug 的复现步骤与影响范围，自动生成后续回归验证方案，内容包括验证环境要求、验证步骤、预期结果、涉及的功能点与回归范围。方案生成后按风险级别决定是否需要人工确认执行规划。

| 项目 | 内容 |
|------|------|
| 输入 | 通过完整性分析的 Bug 任务对象 |
| 输出 | 回归验证方案（步骤化、可执行） |
| 规则 | 可能需要人工确认方案执行规划；高风险模块的验证方案必须经人工确认后方可执行 |

#### 6.1.4 FR-PRE-04 综合难度评分与优先级排序（P0）

系统应基于解决难度、回归验证难度以及改动项（预计修改的代码范围与文件数量）三个维度，对每个 Bug 给出综合难度评分，并按评分进行排序，用于确认后续 Bug 修复优先级；同时依据评分阈值判定该 Bug 是否进入自动修复流程或转人工处理。

| 项目 | 内容 |
|------|------|
| 输入 | Bug 任务对象及其验证方案 |
| 输出 | 各维度评分、综合难度评分、修复优先级队列 |
| 规则 | 评分维度权重可配置；评分结果与排序依据需可查询、可解释 |

### 6.2 Bug 修复模块

Bug 修复模块负责感知缺陷的实际表现，并调用 AI 编码能力完成代码级修复。

#### 6.2.1 FR-FIX-01 对接 Claude Code 进行代码修复（P0）

系统应对接 Claude Code，将 Bug 任务对象、相关代码上下文与修复要求组装为修复指令，驱动其完成代码修改，并自动获取修复结果（变更文件清单、代码差异、修复说明），写入修复任务记录。

| 项目 | 内容 |
|------|------|
| 输入 | 修复任务（Bug 信息 + 代码仓库上下文 + 验证方案要点） |
| 输出 | 修复结果（代码差异、变更说明、执行日志） |
| 规则 | 修复过程需在受控代码分支上进行；修复指令与结果全程留痕，支持审计回放 |

#### 6.2.2 FR-FIX-02 自动感知 Bug 表现（P1）

系统应在修复前后自动感知 Bug 的实际表现，为定位与验证提供依据，感知范围覆盖三个层面：

1. **页面层**——通过界面自动化手段捕获页面渲染异常、元素缺失、交互失效等表现。
2. **数据库层**——检查相关数据记录的完整性、一致性与异常状态。
3. **接口请求层**——捕获接口请求与响应的异常状态码、错误报文与超时情况。

| 项目 | 内容 |
|------|------|
| 输入 | Bug 复现步骤、测试环境访问凭据 |
| 输出 | Bug 表现快照（页面 / 数据库 / 接口三个维度的观测结果） |

### 6.3 回归与验证模块

回归与验证模块负责将修复后的软件部署至测试环境，并依据预处理阶段的方案完成功能验证。

#### 6.3.1 FR-REG-01 测试环境连接与命令行工具支持（P0）

系统应支持连接目标测试环境（服务器、容器或仿真环境），并集成命令行工具能力，可远程执行预定义的命令集（服务管理、文件传输、日志采集等），为自动部署与验证提供基础支撑。

| 项目 | 内容 |
|------|------|
| 输入 | 测试环境连接配置（地址、凭据、命令白名单） |
| 输出 | 可执行的远程命令通道与执行结果回传 |
| 规则 | 命令执行需受白名单约束并记录审计日志 |

#### 6.3.2 FR-REG-02 软件重新打包、更新与启停（P0）

系统应支持对修复后的代码自动完成重新打包、将新版本软件更新至测试环境，并按序完成服务的停止与启动，确保被测版本与修复代码一致。

| 项目 | 内容 |
|------|------|
| 输入 | 修复后的代码分支、打包脚本与部署配置 |
| 输出 | 打包产物、部署结果、服务启停状态 |
| 规则 | 部署失败时应自动回滚至修复前版本并告警 |

#### 6.3.3 FR-REG-03 基于预处理方案的 Bug 功能验证（P0）

系统应依据预处理阶段生成的回归验证方案，在更新后的测试环境中执行 Bug 功能验证，比对实际结果与预期结果，输出验证结论（通过 / 未通过）及过程证据（截图、日志、接口响应）。

| 项目 | 内容 |
|------|------|
| 输入 | 回归验证方案、更新后的测试环境 |
| 输出 | 验证结论与过程证据 |
| 规则 | 验证未通过时触发修复重试；达到重试上限后转入本地记忆阶段处理 |

### 6.4 本地记忆模块

#### 6.4.1 FR-MEM-01 修复过程分类与经验沉淀（P1）

系统应对每次 Bug 修复过程进行分类（如界面类、数据类、接口类、环境类等），将本次修复经验与本地已有经验进行比对，去重、修正后写入修复经验库；经验条目应包含问题特征、修复方法、验证要点与适用条件。

| 项目 | 内容 |
|------|------|
| 输入 | 本次修复全过程记录（任务、修复结果、验证结论） |
| 输出 | 经验分类结果、新增或更新的经验条目 |

#### 6.4.2 FR-MEM-02 不适用场景与人工讨论议题生成（P1）

对于无法自动修复的部分，系统应明确记录不适用场景（何种条件下系统不适用、原因是什么），并自动生成需要与人工进一步讨论的议题清单，推送相关角色处理。

| 项目 | 内容 |
|------|------|
| 输入 | 修复失败记录与失败原因分析 |
| 输出 | 不适用场景说明、待人工讨论议题清单 |

### 6.5 系统属性需求

#### 6.5.1 FR-SYS-01 阶段可扩展（P1）

系统流水线各阶段应采用可插拔设计，支持在不改动整体架构的前提下扩展新阶段（如静态扫描、代码评审、自动提交合并请求等），各阶段通过标准接口传递任务对象与状态。

#### 6.5.2 FR-SYS-02 自我优化迭代（P2，需人工介入）

系统应能基于本地记忆中的经验数据，对修复策略、评分权重、验证方案模板等提出优化建议；所有自我优化迭代必须经过人工评审确认后方可生效，并保留版本记录支持回退。

#### 6.5.3 FR-SYS-03 知识库沉淀输出（P1）

系统应支持将本地经验库中的内容结构化沉淀输出（如导出为知识库文档、检索接口或团队共享 wiki），供团队成员与其他系统查询复用。

## 七、非功能需求

| 类别 | 需求描述 | 目标 / 约束 |
|------|----------|-------------|
| 性能 | 单条 Bug 预处理（含评分排序）耗时；全流程端到端处理时长 | 预处理 ≤ 5 分钟；简单 Bug 端到端 ≤ 30 分钟 |
| 可靠性 | 流水线任一环节失败可恢复，任务状态不丢失；支持断点续跑 | 任务状态持久化，故障恢复后可从断点继续 |
| 安全性 | 测试环境凭据与代码仓库凭据加密存储；命令执行白名单控制；操作全程审计 | 凭据不明文落盘；审计日志保留 ≥ 180 天 |
| 可观测性 | 每个阶段输出结构化日志与运行指标，提供修复任务看板 | 任务全链路可追踪、可回放 |
| 可扩展性 | 新增缺陷平台、新增流水线阶段、新增感知维度可通过配置或插件接入 | 遵循标准接口，不改核心流程 |
| 兼容性 | 支持主流缺陷管理平台与常见部署形态（物理机 / 容器） | 首期至少接入团队在用缺陷平台 |

## 八、人工介入机制

系统并非完全取代人工，而是在关键节点保留人工介入入口。各介入点汇总如下：

| 介入点 | 触发条件 | 人工动作 | 对应需求 |
|--------|----------|----------|----------|
| 信息补充 | 完整性分析判定 Bug 信息不足 | 补充复现步骤、日志、环境等信息 | FR-PRE-02 |
| 方案确认 | 回归验证方案涉及高风险模块 | 确认或调整方案执行规划 | FR-PRE-03 |
| 失败讨论 | 修复重试达上限仍验证未通过 | 评审不适用场景说明，人工接手修复 | FR-MEM-02 |
| 优化评审 | 系统提出自我优化迭代建议 | 评审策略变更，批准后生效 | FR-SYS-02 |

> 介入交互要求：所有人工介入请求应通过消息通知（如企业即时通讯工具）推送至对应角色，包含上下文链接与处理入口；超时未处理的介入请求应按升级策略提醒或自动挂起该任务。

## 九、系统边界与约束

### 9.1 系统边界（范围内）

1. **缺陷处理链路**——覆盖 Bug 获取、预处理、AI 修复、部署、回归验证、经验沉淀的完整链路。
2. **测试环境操作**——仅面向测试环境执行打包、更新、启停与验证操作。

### 9.2 系统边界（范围外）

1. **生产环境操作**——系统不直接对生产环境进行任何变更，生产发布仍走既有发布流程。
2. **缺陷平台管理**——不替代缺陷管理平台本身的功能（如缺陷流转权限、统计报表）。
3. **需求开发**——不处理新需求开发任务，仅处理缺陷修复类任务。

### 9.3 约束条件

1. **AI 能力依赖**——代码修复能力依赖 Claude Code 等 AI 编码服务的可用性与配额。
2. **环境依赖**——自动验证依赖可稳定连接的测试环境与可执行的命令行工具链。
3. **评分准入**——仅综合难度评分低于阈值的 Bug 进入全自动流程，超出阈值的转人工。

## 十、验收标准

| 编号 | 验收项 | 验收标准 |
|------|--------|----------|
| AC-01 | 数据获取与转换 | 可自动拉取缺陷平台 Bug 并生成标准任务对象，字段无丢失 |
| AC-02 | 完整性与补充介入 | 信息缺失的 Bug 能被识别并触发人工补充流程 |
| AC-03 | 验证方案与评分排序 | 每个 Bug 输出可执行的验证方案、三维评分与优先级队列 |
| AC-04 | AI 修复对接 | 可驱动 Claude Code 完成修复并完整记录变更与日志 |
| AC-05 | 自动部署验证 | 自动完成打包、更新、启停，并按方案输出验证结论与证据 |
| AC-06 | 经验沉淀 | 修复完成后经验分类入库，失败场景生成不适用说明与议题 |
| AC-07 | 人工介入 | 四类介入点均可正常触发、通知、处理并回写结果 |
| AC-08 | 指标达标 | 试运行期自动修复成功率与回归通过率达到第 2.3 节目标 |

## 十一、风险与后续规划

### 11.1 主要风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| AI 修复质量不稳定 | 修复结果引入新缺陷 | 回归验证兜底 + 评分准入 + 失败转人工 |
| 测试环境不稳定 | 部署验证失败率高 | 环境健康检查前置，失败自动回滚告警 |
| 缺陷信息质量差 | 预处理大量阻塞在人工补充 | 完善补充请求模板，引导提交人规范填写 |
| 命令执行误操作 | 测试环境服务异常 | 命令白名单 + 审计日志 + 权限最小化 |

### 11.2 后续规划

1. **阶段一（首期）**——打通 P0 需求：预处理全流程、Claude Code 修复对接、自动部署与验证，实现简单 Bug 全自动闭环。
2. **阶段二**——落地 P1 需求：三维 Bug 表现感知、本地记忆与经验库、知识库沉淀输出。
3. **阶段三**——落地 P2 需求：自我优化迭代机制、流水线新阶段扩展（静态扫描、自动评审等），并扩大适用的 Bug 类型范围。
