# Auto BugFixer 整体方案（初稿）

> 状态说明：本文档中的流程细节为草案，范围以 `00-边界定义.md` 为准；
> 待边界定义第 10 节的决策点确认后，再细化本文档的具体流程设计。

## 1. 总体架构

Python 单体项目起步，模块化设计，各模块通过清晰的接口解耦，后续可平滑拆分服务。

```
┌─────────────┐   ┌──────────────┐   ┌───────────────┐
│ Bug 获取模块 │ → │ Bug 分析模块  │ → │ 路由决策        │
│ (API/爬虫)   │   │ (LLM 分类评分)│   │ 全自动/确认/人工 │
└─────────────┘   └──────────────┘   └───────┬───────┘
                                             │
              ┌──────────────────────────────┼──────────────────┐
              ▼                              ▼                  ▼
      ┌───────────────┐            ┌────────────────┐   ┌────────────┐
      │ 自动修复模块    │            │ 人机交互模块     │   │ 仅修复+部署 │
      │ (Claude Code) │            │ (本地审阅文档)   │   │ 人工回归    │
      └───────┬───────┘            └───────┬────────┘   └────────────┘
              ▼                            │
      ┌───────────────┐                    │
      │ 部署模块 (SSH) │ ◄───────────────────┘
      └───────┬───────┘
              ▼
      ┌───────────────┐   失败(≤3轮)   ┌───────────────┐
      │ 自动验证模块    │ ────────────→ │ 回到修复模块     │
      │ (接口断言执行)  │               └───────────────┘
      └───────┬───────┘
              ▼ 通过/最终失败
      ┌───────────────┐
      │ 反馈与沉淀模块  │ → bug 单评论/状态流转/通知 + 模板库与修复记忆库
      └───────────────┘
```

## 2. 技术选型

| 模块 | 选型 | 说明 |
|------|------|------|
| 语言/运行时 | Python 3.11+ | 生态全，团队维护成本低 |
| Bug 系统接入 | REST API 优先；Playwright 兜底 | 无 API 的系统才爬页面 |
| 代码修复 | Claude Code headless（`claude -p --output-format json`） | 子进程调用，结构化解析输出 |
| Bug 分析/计划生成 | LLM API（可与修复共用 Claude） | 结构化 JSON 输出 |
| SSH 部署 | paramiko / fabric | 或直接封装系统 ssh/scp/rsync |
| 接口验证 | httpx + 自研断言执行器 | JSONPath 断言、步骤变量传递 |
| 人机交互 | 本地 Markdown 审阅文档（front-matter 状态字段） | 确认/修改/拒绝均以文档为准；IM/评论仅作可选提醒 |
| 任务编排 | 内存状态机起步（SQLite 持久化） | 不上重型工作流引擎 |
| 模板库/记忆库存储 | JSONL 文件 / SQLite | 验证计划模板 + 修复记忆，按模块索引，后续可扩展向量检索 |
| 配置管理 | YAML + 环境变量 | 密钥走环境变量，不进仓库 |

## 4. 核心流程详细设计

### 4.1 流水线状态机

```
FETCHED → ANALYZED → {AUTO | NEED_CONFIRM | MANUAL_ONLY | REJECTED}
AUTO/NEED_CONFIRM(确认后) → FIXING → FIXED → DEPLOYING → DEPLOYED
  → VERIFYING → {PASSED → REPORTED_DONE | FAILED → FIXING(重试) | EXHAUSTED → MANUAL}
任意失败 → FAILED → 人工接管（bug 单留痕）
```

每个状态迁移写 SQLite，进程重启后可从断点恢复。

### 4.2 分析模块 Prompt 设计要点

输入：bug 标题、描述、复现步骤、预期/实际结果、关联接口文档（如有）、历史验证模板（同模块）。

输出严格 JSON：

```json
{
  "category": "api_logic | flow_combination | ui | env_data | unclear",
  "score": 85,
  "score_reasons": ["..."],
  "verifiable": true,
  "verify_plan": { "steps": [...] },
  "missing_info": [],
  "suggested_template_id": null
}
```

评分阈值（80 / 40）走配置，初期人工复核所有中低分样本，跑一段时间后根据误判率调阈值。

### 4.3 修复模块调用方式

- 前置：流水线全局串行，同一时刻只处理一个 bug；开始修复前校验被修项目工作区干净（`git status` 无未提交改动），不干净则暂停并告警。
- 调用：`claude -p "<bug描述+步骤+上下文>" --output-format json --max-turns N`，工作目录设为项目根。
- 解析：修改文件列表、diff（`git diff`）、Claude 自述。
- 失败重试：把上一次 diff 和失败原因（如验证失败报告）一起喂回去。
- 回滚：修复或验证最终失败转人工时，`git restore` / `git stash` 恢复工作区，保证下一个 bug 从干净状态开始。
- 产物：`data/reports/{bug_id}/fix-round-{n}.diff`。

### 4.4 验证执行引擎

验证计划步骤结构：

```json
{
  "name": "创建订单",
  "request": {"method": "POST", "path": "/api/orders", "body": {...}},
  "extract": {"order_id": "$.data.id"},
  "expect": {"status_code": 200, "body": {"$.code": 0}}
}
```

- `extract` 提取的变量供后续步骤以 `{{order_id}}` 引用。
- 断言支持：状态码、JSONPath 等值/包含/正则。
- 每步记录请求/响应快照，输出整体报告 JSON + 人可读摘要。
- 验证数据清理：计划中可声明 `cleanup` 步骤，无论成败执行。

### 4.5 本地文档审阅协议

所有人工确认点统一走本地审阅文档，确认动作以文档状态字段为准：

- **文档生成**：到达确认点时，系统生成 `data/review/{bug_id}/{type}-review.md`（`type` 为 `verify-plan` / `fix-diff` 等），YAML front-matter 携带状态字段：

```markdown
---
bug_id: BUG-1234
type: verify-plan
status: pending        # pending | confirmed | modified | rejected
reviewer:
reviewed_at:
---

# BUG-1234 验证计划审阅

## Bug 摘要
...

## 分类与评分
api_logic，85 分。理由：...

## 验证计划（可直接编辑）
​```json
{ "steps": [...] }
​```
```

- **审阅操作**：审阅人直接用编辑器打开文档——原样确认改 `status: confirmed`；修改内容后改 `status: modified`；不认可改 `status: rejected` 并在文末注明原因。保存即可。
- **系统检测**：提供 `python main.py resume {bug_id}` 命令显式推进；流水线轮询模式下也会周期性扫描 `pending` 以外的文档并继续流程。`modified` 时以文档内编辑后的验证计划为准替换原计划。
- **提醒（可选）**：生成待审阅文档后可通过 bug 单评论 / 企微 / 钉钉 webhook 发一条提醒，仅告知本地文档路径，不接受远程回复作为确认。
- **超时**：默认 4 小时未审阅升级提醒一次；8 小时仍 `pending` 降级为"修复+部署+人工回归"并在 bug 单注明。
- **留档**：审阅文档（含最终状态与修改痕迹）保留在 `data/review/` 归档，供审计与模板库沉淀使用。

### 4.6 模板库与修复记忆（Memory）

**验证计划模板库**：
- 结构：`{模块/接口路径} → 确认过的验证计划 + 使用次数 + 成功率`。
- 分析新 bug 时检索同模块模板注入 prompt，提高生成质量。
- 人工修改过的计划以人工版本为准覆盖模板。

**修复记忆库（memory）**：
- 存储：`data/memory/` 下按 JSONL 追加写入（或 SQLite 表），每个 bug 一条结构化记录：

```json
{
  "bug_id": "BUG-1234",
  "module": "order",
  "apis": ["POST /api/orders"],
  "symptom_keywords": ["状态不更新", "支付后仍显示待支付"],
  "root_cause": "支付回调未触发订单状态流转",
  "fix_summary": "在 PayCallbackService 中补充状态机流转调用",
  "changed_files": ["src/order/pay_callback.py"],
  "failed_attempts": [{"round": 1, "reason": "只改了查询缓存，验证断言 data.status 仍非 PAID"}],
  "human_corrections": "审阅人在验证计划中补充了金额字段断言",
  "result": "closed",
  "rounds": 2,
  "created_at": "..."
}
```

- 写入时机：每个 bug 处理结束（闭环、转人工或放弃）时由反馈与沉淀模块生成，LLM 辅助从过程日志中提炼。
- 检索复用：第一阶段按 `module` + 关键词匹配检索，取最近 N 条注入分析/修复 prompt；后续迭代可引入向量检索提升相似度匹配能力。
- 与模板库的分工：模板库沉淀"怎么验证"，memory 沉淀"怎么修、踩过什么坑"。

## 5. 配置项（示例）

```yaml
bug_source:
  type: jira                # jira | tapd | zentao | web
  base_url: ...
  filter: "status = Open"   # 轮询过滤条件
poll_interval_seconds: 300

thresholds:
  auto_verify_score: 80
  manual_only_score: 40

fixer:
  command: claude
  serial: true              # 串行逐个处理 bug
  require_clean_worktree: true  # 修复前校验工作区干净
  max_rounds: 3             # 修复-验证最大轮次
  per_round_timeout_minutes: 30
  diff_approval_required: true

deploy:
  target_env: test
  health_check_url: http://test-server/health
  lock: true                # 同环境串行

verify:
  base_url: http://test-server
  timeout_seconds: 60

notify:
  bug_comment: true
  wecom_webhook: ${WECOM_WEBHOOK}
```

## 6. 里程碑计划

| 阶段 | 目标 | 产出 |
|------|------|------|
| M1 骨架跑通（1-2 周） | 单 bug 手动触发：分析 → 修复 → 部署，验证环节人工 | 核心模块 + 状态机 + 一个真实 bug 走通到部署 |
| M2 验证闭环（2-3 周） | 接口验证引擎 + 人工确认交互上线，半自动闭环 | 验证执行器、确认协议、验证报告 |
| M3 全自动试运行（2 周） | 高分 bug 全自动，模板库沉淀 | 路由生效、模板库、运行报告 |
| M4 稳定化 | 监控看板、阈值调优、串行调度健壮性 | 看板、告警、阈值校准 |

M1 建议挑 3-5 个历史真实接口类 bug 回放测试，验证修复和部署环节质量后再进 M2。
