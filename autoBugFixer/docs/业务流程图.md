# autoBugFixer 业务流程图集（Mermaid）

> 本文以当前代码为准（`src/autobugfixer/`），用 Mermaid 绘制系统整体流程与每个阶段的业务流转。
> 每张图附流转要点与代码锚点；静态分层架构见 `docs/diagrams/architecture.mmd`。
>
> 阅读约定：
> - **主干态**：`DISCOVERED → ANALYZING → PLANNING → SCORED → FIXING → DEPLOYING → VERIFYING → LEARNING → CLOSED`
> - **阻塞态**（等外部事件）：`WAIT_INFO / WAIT_PLAN / WAIT_ENV / WAIT_DISCUSS`
> - **终态**：`CLOSED / MANUAL / CANCELLED`；`FAILED` 为可恢复断点态
> - 状态写入契约统一走 `common/core/transitions.py::transition_task`（合法性校验 + 状态历史 + 审计；平台回写为可选钩子，仅编排器侧接线；ingest 建单/唤醒为等效直写留痕，例外见 §15）

---

## 1. 系统总体流程（端到端）


**要点**
- 接入三渠道共用 `ingest_bug` 幂等入口（`features/ingest/ingestion.py`）：新 Bug 建 `BugTicket + Task` 并写 `DISCOVERED → ANALYZING` 历史；已存在则刷新字段，`WAIT_INFO` 且数据变化时自动唤醒。
- 预处理由 `Orchestrator.run_preprocessing` 推进，评分恰好执行一次，准入后停在 `SCORED` 等调度器出队（不自动修复）。
- 平台回写挂在**编排器驱动**的状态迁移上（`status_map` 配置化），失败重试一次后告警，绝不阻塞主流程；调度器/API 侧迁移不回写，见 §15。

## 2. 任务状态机全景（全部合法迁移）

```mermaid
stateDiagram-v2
    state "接入标准化完成" as DISCOVERED
    state "完整性分析" as ANALYZING
    state "待人工补充信息" as WAIT_INFO
    state "生成验证方案" as PLANNING
    state "待人工确认方案" as WAIT_PLAN
    state "评分入队" as SCORED
    state "转人工（终态）" as MANUAL
    state "AI 修复" as FIXING
    state "打包更新启停" as DEPLOYING
    state "等待环境锁" as WAIT_ENV
    state "按方案验证" as VERIFYING
    state "经验沉淀" as LEARNING
    state "失败讨论" as WAIT_DISCUSS
    state "已关闭（终态）" as CLOSED
    state "失败（可断点续跑）" as FAILED

    DISCOVERED --> ANALYZING: 接入完成

    ANALYZING --> WAIT_INFO: 信息或仓库待补充
    ANALYZING --> PLANNING: 完整性通过
    ANALYZING --> MANUAL: 补充往返超上限
    ANALYZING --> FAILED: 阶段异常

    WAIT_INFO --> ANALYZING: 人工/平台数据回流
    WAIT_INFO --> FAILED: SLA 超时挂起

    PLANNING --> WAIT_PLAN: 命中高风险模块
    PLANNING --> WAIT_INFO: 零选定目标仓库
    PLANNING --> SCORED: 低风险方案通过
    PLANNING --> FAILED: 阶段异常

    WAIT_PLAN --> PLANNING: 方案调整重生成
    WAIT_PLAN --> SCORED: 确认通过
    WAIT_PLAN --> MANUAL: 方案被拒绝
    WAIT_PLAN --> FAILED: 阶段异常

    SCORED --> FIXING: 调度器按优先级出队
    SCORED --> MANUAL: 综合分超阈值
    SCORED --> FAILED: 阶段异常

    MANUAL --> ANALYZING: 人工重触发预处理
    MANUAL --> FIXING: 人工重触发修复

    FIXING --> DEPLOYING: 修复产物合格
    FIXING --> LEARNING: 连续两次相同 diff 提前终止
    FIXING --> MANUAL: 触碰禁改路径
    FIXING --> FAILED: 通道失败或零变更

    DEPLOYING --> VERIFYING: 部署成功
    DEPLOYING --> WAIT_ENV: 环境被占用排队
    DEPLOYING --> FIXING: 重试环回修
    DEPLOYING --> FAILED: 部署失败已回滚

    WAIT_ENV --> DEPLOYING: 锁释放被唤醒
    WAIT_ENV --> FAILED: SLA 超时挂起

    VERIFYING --> LEARNING: 全通过或重试耗尽
    VERIFYING --> FIXING: 未通过回修复重试
    VERIFYING --> FAILED: 阶段异常

    LEARNING --> CLOSED: 经验入库并关单
    LEARNING --> WAIT_DISCUSS: 生成失败讨论议题
    LEARNING --> FAILED: 阶段异常

    WAIT_DISCUSS --> MANUAL: 讨论结论 manual_fix
    WAIT_DISCUSS --> CLOSED: 讨论结论 close
    WAIT_DISCUSS --> FIXING: 讨论结论 retry
    WAIT_DISCUSS --> FAILED: 阶段异常

    FAILED --> ANALYZING: 断点续跑回预处理
    FAILED --> FIXING: 断点续跑回修复
    FAILED --> DEPLOYING: 断点续跑回部署
    FAILED --> LEARNING: 断点续跑回沉淀

    note right of WAIT_INFO
        阻塞态：等待人工/平台事件
    end note
    note right of MANUAL
        终态：人工接手，可重新触发
    end note
    note left of FAILED
        所有执行态异常统一落 FAILED；
        API /tasks/{id}/retry 按 current_stage 回到最近可重入状态
    end note
    note right of CLOSED
        终态：迁移时写 closed_at 并回写平台关单
    end note
```

**要点**（对照 `common/core/state.py::LEGAL_TRANSITIONS`）
- `CANCELLED` 为终态，除 `CLOSED/CANCELLED` 外的任意状态（含终态 `MANUAL`）可经 API `POST /tasks/{id}/cancel` 进入（图中略，避免边爆炸）；cancel 同时关闭 pending 介入单并释放持有环境锁，见 §16。
- 断点续跑映射（`api/routes.py`）：`FAILED` 按 `current_stage` → `deploying/verifying→DEPLOYING`、`fixing→FIXING`、`learning→LEARNING`、其余→`ANALYZING`；`MANUAL→ANALYZING`；`WAIT_ENV→DEPLOYING`。
- 状态即断点：worker 只看当前状态路由 Stage，迁移历史完整落 `task_state_history` 可回放。

## 3. 调度器单轮流程（Scheduler.run_round）

```mermaid
flowchart TD
    START(["轮次开始（poll_interval 驱动）"]) --> P1
    P1["① poll_platform<br/>平台拉新，幂等入库"] --> P2
    P2["② preprocess_pending<br/>ANALYZING/PLANNING 推进到评分入队<br/>（含 SCORED 未评分残留补评）"] --> P3
    P3["③ reclaim_stale_env_locks<br/>释放租约过期的环境锁"] --> P4
    P4["④ recover_inflight<br/>孤儿 FIXING/DEPLOYING/VERIFYING/LEARNING<br/>run_until_blocked 续跑（认领租约防撞车）"] --> P5
    P5["⑤ wake_wait_env<br/>锁实际空闲的 WAIT_ENV 任务<br/>每环境每轮只唤醒优先级最高 1 个"] --> P6
    P6["⑥ dispatch_scored<br/>priority_score 升序出队（上限可配）<br/>SCORED→FIXING 迁移后推进"] --> P7
    P7["⑦ scan_intervention_sla<br/>临期提醒 / 超时升级"] --> END(["本轮统计落日志，sleep 后下一轮"])

    P7 -->|"deadline ≤ now<br/>escalation=suspend"| SUS["介入单 timeout<br/>任务置 FAILED + 通知 manager"]
    P7 -->|"deadline ≤ now<br/>escalation=remind"| REM["通知上级角色"]
    P7 -->|"deadline ≤ remind_before"| RMD["提醒处理人"]

    style SUS fill:#fdeff0,stroke:#cf222e
```

**要点**（`runtime/scheduler.py`）
- 顺序刻意安排：先回收锁再唤醒等锁任务，先补评分再出队。
- 单轮各步互相隔离（单任务异常仅记日志，不中断整轮）；`run_forever` 捕获 SIGINT/SIGTERM 优雅停止。

## 4. 编排器执行流程（Orchestrator.run_task）

```mermaid
flowchart TD
    START(["run_task / run_until_blocked"]) --> CLAIM{"原子认领<br/>claimed_until 租约<br/>空闲或已过期？"}
    CLAIM -->|"被他人持有"| SKIP(["返回 None，视同阻塞<br/>绝不并行驱动同一任务"])
    CLAIM -->|"认领成功"| LOOK["查任务当前状态"]
    LOOK --> ST{"阻塞态或终态？"}
    ST -->|"是"| SKIP2(["返回 None"])
    ST -->|"否"| ROUTE["STATE_TO_STAGE 路由<br/>completeness/planning/scoring<br/>fixing/deploying/verifying/learning"]
    ROUTE --> RUN["构建 TaskContext（装配全部服务句柄）<br/>stage.run(ctx)"]
    RUN --> EXC{"Stage 抛异常？"}
    EXC -->|"是"| BD["审计 stage_exception<br/>兜底释放环境锁<br/>迁移 FAILED（可续跑）"]
    EXC -->|"否"| RES{"StageResult 类型"}
    RES -->|"success"| OK["迁移 next_state<br/>（hold_next_states 命中则停在原态留痕<br/>= 预处理准入 HOLD）"]
    RES -->|"need_intervention"| IV["创建介入单（含 SLA deadline）<br/>迁移 intervention.wait_state"]
    RES -->|"retry"| RT["retry_count += 1<br/>迁移 next_state（VERIFYING→FIXING）"]
    RES -->|"failed"| FL["迁移 next_state 或 FAILED"]
    OK --> FIN(["释放认领（finally）"])
    IV --> FIN
    RT --> FIN
    FL --> FIN
    BD --> FIN

    style BD fill:#fdeff0,stroke:#cf222e
```

**要点**（`runtime/orchestrator.py`）
- 认领租约（`task_claim_lease_seconds=900`）保证多执行者（调度器/API/webhook/介入回写）并发安全。
- 四类结果 = 全部 Stage 的出口契约；`run_until_blocked` 循环单步直到阻塞/终态（上限 20 步防环）。
- `run_preprocessing` 只推 `ANALYZING/PLANNING`，`SCORED` 未评分时收尾补评一次——评分恰好执行一次。

## 5. 接入阶段（Ingest）

```mermaid
flowchart TD
    subgraph CH["三个触发渠道"]
        A1["Scheduler.poll_platform<br/>list_bugs 轮询"]
        A2["Webhook 事件<br/>POST /api/webhooks/{platform}"]
        A3["CSV 批量导入<br/>importer/csv_import<br/>（run_analysis 可选附预处理）"]
    end

    A1 & A2 & A3 --> NORM["标准化 BugTicketData<br/>（平台适配器负责）"]
    NORM --> DUP{"platform + platform_bug_id<br/>已存在？"}

    DUP -->|"不存在"| NEW["创建 BugTicket"]
    NEW --> RC["sync_bug_repos 仓库声明校验<br/>切分 repo_url/branch<br/>新仓库自动登记：逐项本地复检（路径/目录/分支）<br/>已登记仓库复用登记表结论，不重复校验<br/>写 bug_repo 行"]
    RC --> CT["创建 Task（DISCOVERED）<br/>写历史 DISCOVERED→ANALYZING<br/>task_ingest 审计含 repo_check 摘要"]
    CT --> OUT(["任务 @ ANALYZING"])

    DUP -->|"已存在"| REF["_refresh_bug 字段刷新<br/>sync_bug_repos 复检（重导场景）"]
    REF --> HAST{"有任务实例？"}
    HAST -->|"无（脏数据兜底）"| CT2["补建任务 + task_recreated 审计"] --> OUT
    HAST -->|"有"| WAKE{"字段实质变化<br/>且任务在 WAIT_INFO？"}
    WAKE -->|"是"| WK["关闭待处理的补充介入单<br/>info_rounds += 1<br/>WAIT_INFO→ANALYZING 重新分析"]
    WAKE -->|"否"| IDLE(["仅刷新，不驱动"])
    WK --> OUT

    style OUT fill:#ebf7ee,stroke:#1a7f37
```

**要点**（`features/ingest/ingestion.py`、`repo_check.py`）
- 幂等以 `platform + platform_bug_id` 为键；重复导入不产生新任务。
- 仓库校验在接入时就完成（0 次 LLM 调用），不可用任务由完整性阶段门禁拦下——越早拦截越省成本。
- Webhook 只在任务停在 `ANALYZING` 时推进预处理：`SCORED` 任务不插队、in-flight 任务不被第二个执行者并发驱动。

## 6. 完整性分析（Completeness）

```mermaid
flowchart TD
    START(["任务 @ ANALYZING"]) --> GATE{"仓库门禁"}
    GATE -->|"声明了仓库：未登记或不可用"| RS
    GATE -->|"未声明：登记表无任何可用仓库"| RS
    GATE -->|"通过"| RULE

    RS{"info_rounds ≥<br/>max_info_rounds？"}
    RS -->|"是"| MU(["→ MANUAL：补充往返超限"])
    RS -->|"否"| IV1(["need_intervention：repo_supplement<br/>→ WAIT_INFO（tester）"])

    RULE{"规则快路径：<br/>6 个必填字段非空？<br/>title/description/repro_steps<br/>expected/actual/env_version"}
    RULE -->|"缺字段"| RS2{"info_rounds ≥ 上限？"}
    RS2 -->|"是"| MU
    RS2 -->|"否"| IV2(["need_intervention：info_supplement（规则判定）<br/>→ WAIT_INFO（tester）"])
    RULE -->|"齐全"| LLM["LLM 评估 completeness<br/>（system/user 双通道 + 失败反馈重试）"]

    LLM --> OK{"complete = true？"}
    OK -->|"否"| RS3{"info_rounds ≥ 上限？"}
    RS3 -->|"是"| MU
    RS3 -->|"否"| IV3(["need_intervention：info_supplement（含 LLM 建议）<br/>→ WAIT_INFO（tester）"])
    OK -->|"是"| PASS(["→ PLANNING：完整性评估通过"])

    style MU fill:#fdeff0,stroke:#cf222e
    style PASS fill:#ebf7ee,stroke:#1a7f37
```

**要点**（`features/completeness/stage.py`）
- 纯门禁阶段（0~1 次 LLM 调用）：仓库画像与 Bug×仓库判定已移至 planning（Spec 02 §9 v3）。
- 三道闸门顺序：仓库门禁 → 规则快路径 → LLM 评估，逐级加深、逐级省钱。
- 信息补充与仓库补充共用 `info_rounds` 止损上限，防补充死循环。
- 唤醒回流：人工 `info_supplement/repo_supplement` 回写或平台数据更新都会把任务带回 `ANALYZING` 复检。

## 7. 方案生成（Planning，含目标仓库选定）

```mermaid
flowchart TD
    START(["任务 @ PLANNING"]) --> SKILL["加载激活技能库<br/>（验证侧经验复用）"]
    SKILL --> CAND["load_repo_candidates<br/>声明链接仓库 + 登记表补选候选<br/>（repo_candidate_limit 限量）<br/>（repo_profile_enabled=false：退化为仅声明链接）"]
    CAND --> PROF["ensure_profiles<br/>候选仓库画像补齐（全局缓存）"]
    PROF --> PROMPT["组装 prompt（v6 双通道）<br/>bug_block（注入安全包裹+截断）<br/>+ 候选登记表（repo_id/路径/分支/画像，包裹边界）<br/>+ 技能库（包裹边界）"]
    PROMPT --> LLM["LLM analyze（max_tokens=8192）<br/>一次调用同时输出：<br/>① DSL 验证方案 ② fix_approach 修复思路<br/>③ target_repos 选仓判定 ④ proposed_skills"]

    LLM --> SAVE["保存 VerificationPlan<br/>（DSL 版本/步骤/预期/回归范围）"]
    SAVE --> SA["_account_skills 技能治理留痕<br/>提议写 skill_proposed<br/>结构命中库内模板判引用 use_count+1"]

    SA --> BIND{"_bind_target_repos<br/>写回 bug_repo<br/>（开关关闭：跳过写回，声明即绑定）"}
    BIND --> B1["声明链接强制保留，判定命中补相关性<br/>未声明判定重建 matched 链接（幂等）<br/>候选集外 id 忽略 + 审计"]
    B1 --> BQ{"存在可用绑定？"}
    BQ -->|"零绑定"| RS{"info_rounds ≥ 上限？"}
    RS -->|"是"| MU(["→ MANUAL"])
    RS -->|"否"| IV1(["need_intervention：repo_supplement<br/>→ WAIT_INFO：请补充仓库声明"])
    BQ -->|"有绑定"| RISK

    RISK{"affected_modules ∩<br/>high_risk_modules？"}
    RISK -->|"命中（high）"| IV2(["need_intervention：plan_confirm<br/>→ WAIT_PLAN（tech_lead）<br/>附方案步骤与命中模块"])
    RISK -->|"未命中（low）"| OK(["priority_score 置空（旧评分作废）<br/>→ SCORED：低风险方案自动通过"])

    IV1 -.->|"补充后回 ANALYZING 复检"| START
    IV2 -.->|"确认/拒绝见介入流程图"| RISK

    style MU fill:#fdeff0,stroke:#cf222e
    style OK fill:#ebf7ee,stroke:#1a7f37
```

**要点**（`features/planning/stage.py`、`completeness/repo_profile.py`）
- 仓库信息在生成**之前**注入 prompt：候选登记表（含全局画像）是输入，`target_repos` 写回只是同一次判定的落库。
- 清 `priority_score` 仅发生在**低风险自动通过**路径（由 `run_preprocessing` 收尾步按未评分重评）；高风险经 `WAIT_PLAN` 确认回 `SCORED` **不清分**：首次进入无碍（收尾步补评），但已有旧评分的续跑场景（如 FAILED 重入规划）确认后会带旧分直接出队（当前代码行为）。
- `repo_profile_enabled=false` 降级：候选仅声明链接、不做 `target_repos` 写回，声明链接即绑定，下游回退基础仓库信息。
- `fix_approach` 是"提示而非约束"：下游修复以实际代码为准。

```mermaid
        R1 -->|"fixing"| R3(["→ FIXING"])
        R1 -->|"learning"| R4(["→ LEARNING"])
        R1 -->|"其余阶段"| R5(["→ ANALYZING"])
        R0 -->|"MANUAL"| R6(["→ ANALYZING 重新预处理"])
        R0 -->|"WAIT_ENV"| R7(["→ DEPLOYING 重试取锁"])
        R0 -->|"其他阻塞/终态"| R8(["不迁移不驱动"])
    end

    R5 & R6 --> DRV["ANALYZING 目标只跑 run_preprocessing<br/>（停 SCORED，受 admission_hold 约束）"]
    R2 & R3 & R4 --> DRV2["FIXING/DEPLOYING/LEARNING 目标<br/>run_until_blocked 同步续跑"]

    style C4 fill:#fdeff0,stroke:#cf222e
    style R8 fill:#f1f3f4,stroke:#6e7781
```

**要点**（`api/routes.py::cancel_task / retry_task`）
- cancel 是唯一能从终态 `MANUAL` 离开的口子；状态迁移、关闭介入单、释放环境锁同事务提交。
- retry 的口径是"回到 `current_stage` 对应的最近可重入状态"，与图 2 中 `FAILED` 的四条出边一一对应；`ANALYZING` 目标只跑预处理（停在 `SCORED`），不自动进修复。
