# Auto BugFixer 需求分析（初稿）

## 1. 背景与目标

测试同事在 bug 管理系统中提交 bug 后，目前需要研发人工阅读 bug 单、定位代码、修复、部署到测试环境，再由测试回归验证。整个流程重复性高、周期长。

本项目目标是构建一套自动化流水线，对**适合自动化的 bug** 实现端到端闭环：

```
读取 bug 单 → 分析可修复/可验证性 → Claude Code 自动修复 → SSH 部署测试环境 → 自动验证 → 结果反馈
```

对于不适合全自动的 bug，系统做自动分级，将人工介入点放在最合适的位置（验证计划确认、修复方案审批、人工回归），而不是"全自动或全人工"二选一。

## 2. 核心设计原则

- **可验证性前置**：在分析阶段就判断该 bug 能否通过接口/数据断言自动验证，决定后续走哪条链路，而不是修完才发现验证不了。
- **人机协同而非全替代**：AI 修复和 AI 验证都不是 100% 可靠，流程中设置人工确认/审批闸门，人工比例随模板沉淀逐步下降。
- **全程可回滚、可追溯**：修复前确保工作区干净，修复 diff、部署日志、验证报告全部存档，失败可回滚。
- **只碰测试环境**：部署目标限定测试/预发环境，不自动触达生产。

## 3. 范围界定

### 3.1 优先支持的场景（In Scope）

- 接口逻辑类 bug：有明确接口请求/响应可断言（URL、入参、预期字段值）。
- 简单业务流程组合类 bug：测试步骤可拆解为"调接口 → 查数据"的序列（如：创建订单 → 查询订单状态 = 已创建）。
- 预期结果为确定性断言的 bug（"返回 status=1"，而非"页面显示美观"）。

### 3.2 暂不自动验证的场景（Out of Scope，仅自动修复+部署，人工回归）

- 纯 UI 交互类 bug（样式、布局、拖拽、富文本、验证码）。
- 依赖复杂前置数据/第三方回调/定时任务的 bug。
- 涉及文件上传下载内容校验的 bug（可后续迭代支持）。

### 3.3 明确不做的事

- 不自动合并代码到主干，不自动上生产。
- 不处理无明确复现步骤、描述不清的 bug 单（打回给测试补充）。

## 4. 用户角色

| 角色 | 与系统的交互 |
|------|------------|
| 测试同事 | 正常提 bug 单；在本地审阅文档中确认/修改验证计划；收到验证报告后复核 |
| 研发同事 | 审批修复 diff（可配置是否必须）；处理系统修复失败的 bug；review 合并 |
| 运维/管理员 | 配置 bug 系统接入、部署脚本、环境信息；监控流水线运行 |

## 5. 功能需求

### 5.1 Bug 获取模块

- 支持从 bug 管理系统拉取待处理 bug 列表（优先 API：Jira / Tapd / 禅道 / 飞书项目；无 API 时用 Playwright 爬取）。
- 读取 bug 单完整信息：标题、描述、复现步骤、预期/实际结果、附件、关联模块。
- 支持轮询新 bug 和按指定 bug 单号触发两种模式。

### 5.2 Bug 分析模块（核心差异化能力）

对每个 bug 产出：

1. **Bug 分类**：接口逻辑类 / 流程组合类 / UI 交互类 / 环境数据类 / 无法确定。
2. **可验证性评分（0-100）**，评分维度：
   - 是否有明确接口可断言
   - 测试步骤是否可转为"调接口 → 查数据"序列
   - 前置数据/账号/环境依赖程度（依赖越多分越低）
   - 预期结果是否为确定性断言
   - 是否涉及文件上传、第三方回调、定时任务等难点
3. **验证计划草案**（机器可执行 JSON），示例：

```json
{
  "verifiable": true,
  "score": 85,
  "type": "api",
  "verify_steps": [
    {"action": "POST /api/orders", "payload": {}, "expect": {"code": 0}},
    {"action": "GET /api/orders/{id}", "expect": {"data.status": "PAID"}}
  ]
}
```

4. **路由决策**：
   - ≥80 分：走全自动链路，验证报告事后推送人工复核。
   - 40-79 分：验证计划草案推送测试同事确认/修改，确认后走自动链路。
   - <40 分：只做自动修复 + 自动部署，标注"需人工验证"。
   - 描述不清/无法分析：打回 bug 单，评论要求补充信息。

### 5.3 人机交互模块（本地文档审阅）

所有需要人工确认的环节，统一采用"本地生成审阅文档 → 人工审阅/修改 → 系统检测确认状态后继续"的方式，不依赖 bug 单评论或 IM 回复：

- 系统在本地审阅目录（`data/review/{bug_id}/`）生成 Markdown 审阅文档，内容包括：bug 摘要、分类与评分及理由、验证计划草案、以及（如涉及）修复 diff 说明。
- 文档头部带状态字段（`status: pending`），审阅人直接在文档上操作：原样确认则将状态改为 `confirmed`；需要修改则直接编辑验证计划内容后将状态改为 `modified`；不认可改 `rejected` 并注明原因。
- 系统通过命令（`resume {bug_id}`）或轮询检测文档状态变化，据此继续流程。
- 通知（bug 单评论 / 企微 / 钉钉）仅作为"有待审阅文档"的提醒手段，为可选配置，确认动作一律以本地文档为准。
- 超时策略：默认 N 小时未审阅则升级提醒，仍无响应则降级为"修复+部署+人工回归"。
- 所有审阅文档及最终状态留档，作为审计依据。

### 5.4 自动修复模块

- **串行逐个处理**：同一时刻只处理一个 bug，直接在当前工作区修改；修复前校验工作区干净（无未提交改动），处理完一个（闭环或转人工）才取下一个。
- 失败回滚：修复或验证失败转人工时，通过 `git restore` / `git stash` 将工作区恢复到修复前状态，避免污染后续 bug 的处理。
- 调用 Claude Code headless 模式（`claude -p ... --output-format json`）执行修复，输入：bug 描述 + 复现步骤 + 相关代码路径 + 项目上下文。
- 解析 Claude Code 输出：修改文件列表、diff、自描述说明。
- 修复失败或超时时自动重试（带上一次失败信息），上限可配置（默认 2 次），最终失败转人工并记录原因。
- 可选闸门：修复 diff 生成本地审阅文档（同 5.3 机制），研发审阅通过后才允许部署。

### 5.5 部署模块

- 通过 SSH（paramiko / fabric / 系统 ssh）将构建产物部署到指定测试环境。
- 支持配置化部署流程：拉代码 → 构建 → 换包 → 重载服务 → 健康检查。
- 部署失败自动回滚到上一版本并告警。
- 部署完成后等待服务就绪（健康检查通过）再进入验证环节。

### 5.6 自动验证模块

- 执行验证计划：按步骤调接口、断言响应（支持 JSONPath 式字段断言、状态码断言、步骤间变量传递如 `{id}`）。
- 验证环境数据隔离：验证产生的数据带标识，可清理。
- 验证结果产出报告：每步请求/响应/断言结果、整体通过与否、失败步骤详情。
- 验证失败时，将失败信息反馈给修复模块再修一轮（总轮次上限默认 3 次）。

### 5.7 反馈与沉淀模块

- 验证通过：bug 单自动评论验证报告，状态流转（如"待测试复核"），通知测试同事复核。
- 验证失败/修复失败：bug 单评论失败详情，转人工处理。
- 确认过的验证计划沉淀为模板库，按模块/接口索引，供后续同类 bug 复用，逐步提高评分准确性和全自动比例。
- **修复记忆（memory）持久化**：每个 bug 处理结束后（无论成败），将本次处理经验结构化写入持久化记忆库：
  - bug 特征：所属模块、涉及接口、错误现象关键词；
  - 根因与修复方法：Claude Code 定位到的根因、最终生效的修复方式、修改的文件；
  - 失败教训：中途失败的修复尝试及失败原因（如验证不通过的断言）；
  - 人工修正：审阅人对验证计划/修复 diff 的修改点；
  - 结果：是否闭环、修复轮次。
- **memory 复用**：处理新 bug 时，在分析阶段和修复阶段检索同模块/相似现象的历史 memory 注入 LLM 上下文，让系统"越修越准"，提升一次修复成功率、减少重复踩坑。

### 5.8 审计与监控

- 每个 bug 全链路日志：分析结果、修复 diff、部署日志、验证报告，可查询可追溯。
- 运行指标看板（后续迭代）：处理 bug 数、全自动率、一次修复成功率、验证通过率。

## 6. 非功能需求

- **安全性**：bug 系统凭据、SSH 密钥、LLM API Key 统一配置管理，不硬编码；测试环境访问受限。
- **隔离性**：串行逐个处理 bug（同一时刻只处理一个），避免并发污染工作区与测试环境；同一环境部署加锁。
- **可扩展性**：bug 系统接入、LLM 调用、部署流程均插件化/配置化，便于接入新系统或换 LLM。
- **成本控制**：记录每个 bug 的 LLM token 消耗，支持单 bug 消耗上限。

## 7. 关键风险与对策

| 风险 | 对策 |
|------|------|
| Claude Code 修复跑偏/引入新问题 | 串行处理 + diff 审批闸门 + 验证闭环 + 失败回滚工作区 |
| 自然语言测试步骤转验证计划不准确 | 中分档强制人工确认；模板库沉淀复用 |
| 接口验证误报（环境/数据问题） | 部署后健康检查；验证数据隔离；失败详情留痕便于人工判断 |
| 并发处理导致环境冲突 | 同一部署环境加锁串行 |
| bug 单信息不足 | 分析阶段识别并自动打回要求补充 |

## 8. 成功度量（上线后观察）

- 全自动闭环率（无需人工介入完成的 bug 占比）
- 一次修复成功率、平均修复轮次
- 人工确认平均响应时长
- 误判率（验证通过但人工复核不通过的比例）
