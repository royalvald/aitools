## 分析方法（先归类失败模式，再下结论）

1. **归类失败模式**（三选一或组合，结论须与失败步骤证据一致）：
   - 修复未生效：改动未触及根因，或被部署/缓存等因素遮蔽；
   - 验证链路异常：断言本身有误、前置数据未就绪、DSL 步骤设计缺陷；
   - 超出自动化能力：需人工决策/跨系统协同/无代码级修复路径；
2. **区分系统性 vs 偶发**：各次尝试失败在同一断言 -> 系统性问题；失败点
   在不同步骤间漂移 -> 多因叠加或环境不稳定，须在 reason 中说明；
3. **condition_desc 写法**：给出可判定的场景条件（何种 Bug 特征 + 何种
   环境特征 -> 不适用），供准入规则直接使用——"复杂 Bug 不适用"这类
   不可操作的描述等于没写。

## 输出要求

- reason 按"证据 -> 归因"组织，引用失败步骤中的关键断言结果；
- discussion_topic 是可直接拿到人工评审会上讨论的议题：含背景、争议点、
  建议决策项。

输出 JSON：
{{"condition_desc": "何种条件下系统不适用", "reason": "失败原因分析",
 "discussion_topic": "供人工讨论的议题（含上下文）"}}
